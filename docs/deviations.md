# Deviations and Decisions

The dev bible (`docs/dev-bible.md`) is canonical (§100). Any place where the implementation
differs from it, or fills a gap it leaves open, is recorded here deliberately.

| ID    | Date       | Area                    | Decision                                                                                                                                                                                                                                       | Reason                                                                                                                                                                                                                                                                 |
| ----- | ---------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-001 | 2026-10-02 | Local development       | Local Postgres 16 stands in for Supabase PostgreSQL; SeaweedFS (S3 API) stands in for Cloudflare R2. **Local and test only.** Production remains Supabase + R2.                                                                                | No managed services reachable from development containers. Both stand-ins sit behind the same interfaces (`pg` connection string, S3 API) so no code path differs.                                                                                                     |
| D-002 | 2026-10-02 | Connectors (§61)        | P0 PSA is **ConnectWise PSA**; P0 RMM is **NinjaOne**. P0 order: Entra → Sentinel → ConnectWise PSA → NinjaOne. P1: CrowdStrike → AWS / Azure → HaloPSA / Autotask / N-able / Datto as demanded.                                               | Product owner decision; removes the wait for a design partner.                                                                                                                                                                                                         |
| D-003 | 2026-10-02 | Libraries (§97)         | Adopted **BullMQ** (queues), **Zod** (validation), **otplib** (TOTP), and **custom opaque sessions** (no auth framework).                                                                                                                      | Small, standard, each materially improves reliability or simplicity. BullMQ makes Redis operational infrastructure: jobs must be idempotent and every evidence-processing job is also recorded in PostgreSQL. Redis is never the only record that a job existed (§48). |
| D-004 | 2026-10-02 | Typography (§78)        | Manrope and IBM Plex Mono are self-hosted via `@fontsource` packages.                                                                                                                                                                          | No third-party font requests from a security product; builds don't need network access to a font CDN.                                                                                                                                                                  |
| D-005 | 2026-10-02 | Theme tokens (§76)      | Filled gaps: Limestone `text-muted #5F5D58`, `status-critical #A84A46`, `bg-elevated #E8E1DA`; Midnight `bg-elevated #223643`.                                                                                                                 | The bible does not specify these tokens; values are derived from the existing palettes.                                                                                                                                                                                |
| D-006 | 2026-10-02 | Toolchain               | TypeScript pinned to 6.0.x.                                                                                                                                                                                                                    | `typescript-eslint` does not yet support TypeScript 7.                                                                                                                                                                                                                 |
| D-007 | 2026-10-02 | Repository layout (§57) | The repository root _is_ the monorepo (no nested `platform/` directory).                                                                                                                                                                       | Equivalent structure, one less level of nesting.                                                                                                                                                                                                                       |
| D-008 | 2026-10-02 | RBAC (§27, §101)        | Added `incident:view` and `audit:view` permissions. Roles and role→permission mappings are defined in code (`packages/auth/src/permissions.ts`) rather than `roles`/`permissions` tables.                                                      | The bible's list has no read permission for incidents or the audit log. Custom roles are not a requirement yet; code-defined mappings are versioned in git and reviewed. Tables can be added if customer-defined roles become a feature.                               |
| D-009 | 2026-10-02 | Repository layout (§57) | Added `packages/audit` (application audit-log writer).                                                                                                                                                                                         | Audit logging (§67) is used by every module; a dedicated package keeps it isolated and avoids `shared` depending on the database.                                                                                                                                      |
| D-010 | 2026-10-02 | Authentication (§107)   | Step-up re-authentication requires password **and** a second factor, so users must enrol MFA before using step-up-protected permissions. Session defaults: 12 h absolute, 30 min idle, 10 min step-up window, lockout 15 min after 5 failures. | Step-up with only a password adds little over the existing session. Values are configuration, not constants.                                                                                                                                                           |
| D-011 | 2026-10-02 | Schema (§101)           | The §101 table families are created module by module as each is built, rather than all at once in Milestone 1.                                                                                                                                 | Creating dozens of tables before their module is designed would force rework migrations; applied migrations are immutable (§125).                                                                                                                                      |
| D-012 | 2026-10-02 | Repository layout (§57) | Added `packages/jobs` (job records, outbox, BullMQ runtime).                                                                                                                                                                                   | Both `web` (enqueue in business transactions) and `worker` (execute) need it; it is infrastructure, not a domain module.                                                                                                                                               |
| D-013 | 2026-10-02 | Source envelope (§38)   | Envelopes add `objectType` and `sourceApi` to the §38 fields.                                                                                                                                                                                  | Provenance requires knowing which API and object kind produced the artifact (§111). Purely additive.                                                                                                                                                                   |
| D-014 | 2026-10-02 | Worker packaging (§53)  | The worker is bundled with esbuild into a single file including its dependencies; the image ships only `dist/`.                                                                                                                                | Smaller image, no dependency resolution at runtime, identical behaviour locally and in production.                                                                                                                                                                     |
| D-015 | 2026-10-02 | Storage layout (§109)   | Added `tenant/{id}/quarantine/...` for objects that could not form a valid envelope, and `manifests/{id}.json.sig` beside each manifest.                                                                                                       | Quarantined objects must be preserved, not dropped (§1.3); export bundles need the detached signature (§23).                                                                                                                                                           |
| D-016 | 2026-10-02 | UI components (§84)     | Kokonut UI registry is unreachable from the build environment (network policy) and is not published to npm. Components follow the shadcn/ui pattern Kokonut builds on (Radix primitives + Tailwind + cva), skinned with our tokens.            | Same foundation Kokonut uses; Kokonut components can be added to `components/ui` without restructuring once the registry is reachable.                                                                                                                                 |
| D-017 | 2026-10-02 | Integrity (§41)         | Manifests use RFC 6962 Merkle hashing (domain-separated leaves/nodes), leaf data `evidenceId:rawSha256`, partitioned by tenant + source + ingestion hour, one hash chain per tenant, Ed25519 signatures over canonical JSON.                   | Standard, independently re-implementable (offline verifier) and binds object identity to content.                                                                                                                                                                      |
